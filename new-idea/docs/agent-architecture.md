# Agent 架构设计（基于 ECC + Superpowers 四层重构）

> 版本：2.0.0  
> 设计依据：[ECC](https://github.com/affaan-m/ECC)（上下文经济学 + 多智能体编排 + 记忆持久化）+ [Superpowers](https://github.com/obra/superpowers)（技能驱动工作流 + 子代理 + 证据优于断言）。  
> 目标：让整个需求挖掘框架从"单一流水线脚本"升级为**专业 Agent 架构**——感知层、推理层、行动层、记忆层四层解耦、可独立扩展。

---

## 一、四层架构总览

```
┌─────────────────────────────────────────────────────────┐
│                    记忆层 Memory                        │
│   • data/<company>/*.json  案例事实库（证据/需求/评分） │
│   • data/<company>/raw/    原始素材库（voices/竞品/研究）│
│   • harness/*.mjs          契约与基线（rules/qa/lock）  │
│   • docs/*.md              方法论记忆（SOP/标准/纪律）  │
└───────────────────────────────┬─────────────────────────┘
                                │ 读取 / 写入
┌───────────────────────────────▼─────────────────────────┐
│                    感知层 Perception                    │
│   • 数据源差异化配置 dataSourceStrategy（按客群地理定向）│
│   • 采集动作：Amazon/Reddit/Trustpilot/竞品/趋势/行业    │
│   • 三级核验 L1/L2/L3 首次接入                          │
└───────────────────────────────┬─────────────────────────┘
                                │ 原始证据流
┌───────────────────────────────▼─────────────────────────┐
│                    推理层 Reasoning                     │
│   • 信息源推导逻辑：场景→痛点→竞品缺口→趋势→需求        │
│   • 根因多点验证（≥2 独立来源 cross 交叉）              │
│   • 三专家评审（产品/市场投资/用户）× 八维评分           │
│   • 市场验证闭环（用户声音/竞品/行业/参考行业/市场声音） │
└───────────────────────────────┬─────────────────────────┘
                                │ 结论流（IDEA + 评分 + 证据链）
┌───────────────────────────────▼─────────────────────────┐
│                    行动层 Action                        │
│   • 产出：prd-draft.md / 单文件 HTML 报告                │
│   • 质量闸门：QA（0 ERROR）→ lock（基线）→ build（渲染） │
│   • 发布：Git 提交 + GitHub Pages 部署                   │
└───────────────────────────────┬─────────────────────────┘
                                │ 反馈/学习
└─────────────── 回流至记忆层（qa 结果、评审意见、基线哈希）┘
```

## 二、各层职责与组件（可扩展点）

### 2.1 感知层（Perception）— 采集与核验

**职责**：决定"从哪些渠道、采集什么、如何核验"。

| 组件 | 现状实现 | 扩展点 |
|------|---------|--------|
| 数据源差异化配置 | `company-profile.json.dataSourceStrategy`（按客群地理） | 新增市场预设模板（海外/国内/东南亚） |
| 三级核验 | `evidence-standard.md` L1/L2/L3 + `verification.json` | 接入真实爬虫/API 自动核验 URL |
| 原始素材归档 | `raw/voices|competitors|research/` 命名 `T{n}_{渠道}_{日期}_{关键词}` | 新增 RSS/评论抓取脚本 |
| Skill 感知 | 加载 competitive-analysis-zh / gemini-deep-research | 按客群地理选技能 |

**解耦原则**：感知层只负责"拿到带出处的原始证据"，不做判断。证据必须含 `url + date + tier + level`，否则无法进入推理层。

### 2.2 推理层（Reasoning）— 推导与判断（本架构核心）

**职责**：把原始证据转化为"有强支撑的需求结论"。这是信息源推导逻辑所在，也是本次重构重点。

**信息源推导逻辑（关键设计）**：

```
输入：原始证据集合 { E## }
    │
    ├── ① 场景-痛点推导（scene-pain）
    │     用户声音(≥2不同平台L3) → 聚类痛点 → 是否高频高痛？
    │
    ├── ② 竞品-缺口推导（competitor-gap）
    │     竞品已上功能(L2) + 我方无(L1核验) → 是否同类可比？
    │
    ├── ③ 跨行业-迁移推导（cross-industry）
    │     他行业已验证方案 → 本行业对应场景是否存在？
    │
    └── ④ 汇总为需求候选 IDEA
         每个 IDEA 必须走「市场验证闭环」才能进 TOP5：
         用户声音（L3） + 竞品验证（L2） + 行业验证（L1/L2）
         + 参考行业验证（cross-industry） + 市场声音（Tier3 趋势）
         → 全部强支撑该功能，缺一不可
```

**推导规则（写入 rules.mjs，QA 强制）**：
- 根因须 ≥2 个独立来源交叉（`cross` 字段）
- 每个 TOP5 需求须满足市场验证闭环（见 `docs/market-validation-loop.md`）
- 单一来源 → 降级为"假设/待验证"，不得进根因表述

### 2.3 行动层（Action）— 产出与交付

**职责**：把推理结论固化为可交付产物，并做质量把关。

| 组件 | 现状实现 | 说明 |
|------|---------|------|
| PRD 产出 | `prd-draft.md` | 标准大厂格式 |
| 报告渲染 | `templates/report-template.html` → `output/index.html` | 单文件 HTML |
| 质量闸门 | `harness/qa.mjs`（0 ERROR） | 15+ 项检测 |
| 基线锁定 | `harness/lock.mjs`（SHA-256） | 防内容漂移 |
| 发布 | Git 提交 + GitHub Pages | 独立 gh-pages 分支 |

### 2.4 记忆层（Memory）— 持久化与复用

**职责**：跨会话保存事实、契约、方法论，供感知/推理/行动层复用。

| 记忆类型 | 位置 | 说明 |
|---------|------|------|
| 案例事实库 | `data/<company>/` | 证据/需求/评分/核验 JSON |
| 方法论记忆 | `docs/*.md` | SOP/标准/纪律/评分模型/数据源策略 |
| 契约与基线 | `harness/rules.mjs` + `*.lock.json` | 评分阈值、QA 规则、SHA-256 基线 |
| 技能记忆 | `.codebuddy/skills/`（superpowers） | 复用工程化工作流 |

**ECC 记忆原则落地**：会话结束后将重要信息蒸馏为结构化 JSON（而非原始转录），跨会话/跨公司共享方法论（docs），基线哈希保证内容可审计。

## 三、信息源推导逻辑的强支撑约束

**问题**：旧架构允许"证据存在但彼此孤立"的伪支撑——比如一条 IDEA 挂了 3 条证据，但证据分属不同维度且互不验证。

**本架构强制**：每个新功能 IDEA 的产出，必须满足"五源强支撑"（见 `docs/market-validation-loop.md`）：

| 支撑源 | 对应证据类型 | 最小要求 | 强支撑逻辑 |
|--------|------------|---------|-----------|
| ① 市场声音 | 行业报告/市场规模（L2, Tier1） | ≥1 | 证明市场够大且在增长 |
| ② 竞品验证 | 竞品已上功能（L2） | ≥1 | 证明同类已被市场接受 |
| ③ 行业验证 | 行业趋势/报告（L1/L2） | ≥1 | 证明处于上升通道 |
| ④ 参考行业验证 | 跨行业迁移成功案例（cross-industry） | ≥1 | 证明路径可复用 |
| ⑤ 用户声音 | 真实用户评论/社区（L3, Tier2） | ≥2 不同平台 | 证明真实痛点非伪需求 |

> 只有**全部 5 类源头数据都强支撑**该功能，才判定为"真实需求"进入 TOP5；缺任何一类，该 IDEA 降级至功能清单或观察池。

## 四、解耦与可扩展设计

- **层间接口**：各层通过 `data/<company>/` 的 JSON 文件通信（感知写 raw/evidence → 推理读→写 ideas/scores → 行动读→渲染）。改动某层不影响其他层。
- **新增感知源**：只需新增采集脚本写 raw/，无需改推理/行动层。
- **新增推理规则**：只需在 `harness/rules.mjs` 增字段 + `harness/qa.mjs` 增检测。
- **新增产出形态**：行动层新增渲染模板即可。

## 五、与 Superpowers / ECC 的映射

| 本架构层 | Superpowers 技能 | ECC 组件 |
|---------|-----------------|---------|
| 感知层 | `brainstorming`（对齐采集范围） | Hooks / Contexts / MCP |
| 推理层 | `writing-plans`（拆解推导） | 68 Agents（planner/architect） |
| 行动层 | `executing-plans` + `subagent-driven-development` + `verification-before-completion` | 94 Commands + Verification Loops |
| 记忆层 | `writing-skills`（沉淀方法论） | Memory Vault + Continuous Learning |

工作流顺序（每次新公司都走）：
`brainstorming（感知对齐） → 采集（感知） → 推导（推理，含市场验证闭环） → executing-plans（行动） → verification-before-completion（验证） → writing-skills/memory（记忆回流）`
