# 工作流审视报告 — 置信度与规范约束优化

> 审视日期：2026-08-11
> 方法：superpowers 方法论（verification-before-completion / test-driven-development / systematic-debugging 视角）
> 范围：3C 竞品分析框架的完整工作流（采集 → 证据 → PRD → harness → 构建 → 发布）

## 一、审视目标

确保每次产出的**置信度**与**规范约束**稳定可复现，消除"看起来完成了"的假性交付。

## 二、诊断发现（按严重度排序）

### 🔴 HIGH-1：幽灵证据引用（置信度致命）
- **现状**：`checkNumericClaims` 用 ±200 字符上下文匹配 `E\d{3}`，但**不校验引用的 E## 是否真实存在**于 `evidence.json`。
- **风险**：PRD 可引用 `E999` 等不存在的证据编号，QA 仍然通过 → 违反"数据溯源"硬规则，报告出现无源头断言。
- **修复**：构建/QA 时校验 PRD 引用的每个 E## 都存在于 `evidence` 数组；同时校验所有 E## 是否被至少 1 个优化点使用（防孤儿证据）。

### 🔴 HIGH-2：断言纪律检测缺失
- **现状**：`claim_discipline` 要求"只能分析可观测行为，不得推测内部算法/策略/运营"，但 QA **未检测不可观测行为推测**。
- **风险**：产出可能出现"优化降噪算法""调整运营策略""更换供应链"等伪需求，违反红线 2。
- **修复**：在 `rules.mjs` 增加 `UNOBSERVABLE_BEHAVIOR` 模式，qa 落 ERROR 拦截。

### 🟠 MED-3：E##/V## 对应关系未校验
- **现状**：`verification.json` 的 V## 是否与 E## 一一对应、`final_level` 是否合法（L1/L2/L3）、`verified_at` 是否时间戳——当前均未校验。
- **风险**：核验记录可与证据脱节，三级核验形同虚设。
- **修复**：校验每个 E## 有且仅有 1 条对应 V##，`final_level` 取值合法。

### 🟠 MED-4：web-design-engineer 设计规范未固化
- **现状**：build.mjs 机械替换占位符，无设计质量门槛；报告设计未遵循 web-design-engineer 的"设计系统声明、反陈词滥调、精选字体色彩"原则。
- **风险**：报告视觉质量波动，产生趋同的 AI 设计（Inter 字体 + 蓝紫渐变 + 大圆角卡片）。
- **修复**：build.mjs 注入"设计系统声明"区块（字体/色彩/间距令牌），qa 检测模板是否含设计令牌与反陈词滥调约束。

### 🟡 LOW-5：superpowers 流程与 harness 未衔接
- **现状**：superpowers 流程是软约束（写文档、走审查），未落到硬性质量门槛。
- **修复**：把"验收"落到 QA——构建前必须 qa 全绿；发布前必须 lock 基线；内容变更必须重新 lock。

### 🟡 LOW-6：PowerShell 执行策略导致脚本不可直接运行
- **现状**：`scripts/new-category.ps1`、`publish.ps1` 依赖 PowerShell，但系统默认禁止脚本执行。
- **修复**：AGENTS.md 中补充 `Set-ExecutionPolicy -Scope Process Bypass` 提示，或建议用 cmd/node 调用。

## 三、优化方案

### 3.1 Harness 强化（rules.mjs + qa.mjs）

新增检测项：
| 检测 | 严重度 | 触发条件 |
|------|--------|----------|
| `checkGhostRefs` | ERROR | PRD 引用不存在的 E## |
| `checkOrphanEvidence` | WARNING | E## 未被任何优化点使用 |
| `checkUnobservable` | ERROR | 出现"算法优化/策略调整/运营手段"等不可观测词 |
| `checkEvidenceVerification` | ERROR | E## 无对应 V## / final_level 非法 |
| `checkDesignTokens` | WARNING | 模板缺少设计系统声明令牌 |

### 3.2 构建管线强化（build.mjs）

- 注入设计系统声明区块（在 HTML 头部生成 Design Tokens）
- 构建前对 PRD 引用做证据存在性校验（阻断幽灵引用）

### 3.3 AGENTS.md 固化

- 明确"三阶段验收闸门"：采集后 QA → 发布前 Lock → 变更后 Relock
- 衔接 superpowers 流程与 harness 硬约束
- 引入 web-design-engineer 设计规范为报告设计要求

## 四、验收标准

每次稳定产出必须满足：
1. `node harness/qa.mjs` 0 ERROR（8 → 13 项全绿）
2. 报告 HTML 含设计系统声明，无 AI 黑话，无幽灵引用
3. 证据与核验一一对应，无孤儿证据
4. 发布前基线已锁定
